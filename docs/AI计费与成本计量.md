# AI 计费与成本计量（服务端 1.5.0 / 1.6.0）

> 本文讲**已落地**的计量能力（1.5.0 阶段一）与余额域（1.6.0 阶段二核心），
> 以及按量计费改造的完整路线与待决策点。

---

## 1. 为什么必须改：旧模型的三条硬伤

改造前的计费口径是「**次数**」：`gatewayChat()` 把上游响应 `pipe` 给客户端，只在
`upstream.statusCode < 400` 时 `countUsage()` 记 +1。**全链路不解析 `usage`、不记 token、
不记成本**，`channels.json` 里也没有任何模型单价字段。

由此产生三个问题：

| # | 问题 | 说明 |
|---|---|---|
| 1 | **次数口径与成本口径脱钩** | 翻译一整篇 PDF 与问一句「什么是 DOI」，在计费上都是「1 次」，实际成本差 2–3 个数量级。「免费 100 次/日」「专业版 3000 次/日」实际是**两张金额不受控的支票**。 |
| 2 | **永久会员 = 无限期成本负债** | ¥128 买 3000 次/天「永久」：收入一次，之后每一天都在产生新的上游成本。这不是预收款，是卖出无限责任。 |
| 3 | **无数据支撑定价** | 没有任何人均成本数据，任何定价尝试都是拍脑袋。 |

结论：**先让成本可见，再谈定价与余额。** 阶段一（1.5.0）只做这一件事。

## 2. 计量口径（三条约定的铁律）

### 2.1 成本用「微元」整数，不用「分」

一次短问答可能只值 ¥0.0008。若以「分」累计，每一笔都被四舍五入成 0，跑一个月也看不到成本。

- **微元** = 1e-6 元；1 元 = 1e6 微元；1 分 = 1e4 微元。
- 单价单位是「**元 / 千 token**」，换算公式：

```
cost(元)   = inTok/1000 * inPer1k + outTok/1000 * outPer1k
cost(微元) = (inTok * inPer1k + outTok * outPer1k) * 1000        ← 整数，累加无漂移
```

### 2.2 ★ 按「响应里的真实模型」计价，不按请求里的模型

客户端最常用的是 `auto`，它由上游映射成真实模型，**响应里的 `model` 字段会回填真名**。
若按请求计价，所有 `auto` 请求都会被记到键名 `"auto"` 下，成本统计彻底失真。

代码落点：`const billModel = respModel || requestedModel;`

### 2.3 ★ 上游没给 `usage` ≠ 0 成本，而是「未知」

`usageOf()` 在完全取不到有效 token 时返回 `null`，此时：

- 只计次数，并把 `user.usage.missingUsage` +1（**计量盲区**）；
- **不写入 `byModel`**（避免伪造一条 0 成本记录）；
- 后台看板与 `/api/health` 都会显著提示。

绝不静默当成免费——那是「免费额度被无声掏空」的典型成因。

### 2.4 单价匹配只做精确（含忽略大小写），**不做前缀匹配**

`glm-5.3` 是 `glm-5.3-flash` 的前缀，但两者单价不同。前缀匹配会把贵模型的钱按便宜模型的价结算
——**算错钱比不算是更糟的失败**。未配价的模型一律回落 `fallback`（默认 0）并标 `known=false`，
由后台列出让人补。

## 3. 数据落点

### 3.1 `server/data/pricing.json`（新增，已纳入快照）

```json
{
  "schemaVersion": 1,
  "currency": "CNY",
  "models": {
    "glm-5.3-flash": { "inPer1k": 0.0008, "outPer1k": 0.002, "note": "", "updatedAt": "..." }
  },
  "fallback": { "inPer1k": 0, "outPer1k": 0 }
}
```

`backup.js` 的 `FILES` 已加入 `pricing.json`；`reloadStores()` 会一并重载，
保证快照回滚后内存与磁盘同步。

### 3.2 `user.usage` 扩展（**零迁移**，旧字段一个没动）

```
{
  date, count,                 // 旧契约（1.4.x），语义完全不变
  daily: { 'YYYY-MM-DD': n },  // 次数趋势（1.4.3）
  // ——— 1.5.0 新增 ———
  inTok:      { 'YYYY-MM-DD': n },   // 输入 token
  outTok:     { 'YYYY-MM-DD': n },   // 输出 token
  costMicro:  { 'YYYY-MM-DD': n },   // 当日成本（微元）
  byModel:    { '<模型>': { n, inTok, outTok, costMicro, lastAt } },   // 全时段累计
  missingUsage: n                    // 上游未返回 usage 的次数
}
```

> **纪律**：`daily` 必须保持 `number`。所有 1.4.x 的读取点（`usageDays`、面板趋势图、
> 后台列表）都直接 `Number(daily[key])`——一旦改成对象就是**静默的读出 undefined**。
> 所以 token / 成本另开三张并行映射，而不是把 `daily` 升级成对象。

保留 30 天（`USAGE_KEEP_DAYS`），四张按日映射同步裁剪。

## 4. 网关改造要点

| 点 | 做法 | 为什么 |
|---|---|---|
| 流式计量 | 请求注入 `stream_options.include_usage = true` | 主流 OpenAI 兼容上游**默认不返回**流式 usage；不注入则流式完全无法计费 |
| 通道级开关 | `channel.streamUsage`（默认 `true`） | 个别上游不认该参数会直接 400，需要能关 |
| 转发与解析并行 | 手动 `res.write` 替代 `upRes.pipe(res)`，顺带 tee 解析 | `pipe` 无法旁路读取 |
| 流式解析内存 | 逐行扫描，只保留未成行的尾巴，超 1MB 截断到 4KB | 缓冲不随响应体量增长 |
| 非流式解析 | 缓冲响应体解析 `usage`；超过 4MB 放弃解析 | 只影响计量，不影响转发 |
| 上游 4xx | **不计次**（保持 1.4.x 旧口径） | 上游是否已产生成本无从得知，口径不宜在同一版本内悄然改变 |
| 背压 | `res.write()` 返回 false 时 `upRes.pause()`，`drain` 后恢复 | 取代 `pipe` 后需自行处理 |

## 7. 运维手册

**每天做什么**：打开 `/admin` → 「成本与用量」，看三件事：

1. **未配价模型** 是否为空。不为空 → 立刻在「模型单价表」里补价，否则成本统计偏低估。
2. **计量盲区** 是否为 0。持续增长 → 上游该通道不返回 usage，考虑关掉该通道的 `streamUsage`
   或换通道（盲区意味着「有调用但成本未知」）。
3. **人均成本**。这是定价的核心输入——阶段二定价的倍率就建立在它之上。

**配价从哪来**：问上游（Prism 网关 / 各模型厂商）拿「元 / 千 token」的进价，输入价与输出价分开填。
**进价 + 毛利倍率 = 零售价**，倍率建议见下节。

## 8. 阶段二：余额域（1.6.0 核心已落地）

### 8.1 现状

**已落地（服务端 1.6.0）**：

| 能力 | 说明 |
|---|---|
| 余额结构 | `user.balance = { grantedMicro（赠送,有期）/ paidMicro（充值,永不过期）/ ledger }`，随 users.json 走既有快照/回滚 |
| 注册赠送 | 自动发放（默认 ¥6 / 30 天，配置驱动；幂等，重复发放跳过） |
| 按成本扣减 | 网关按真实成本扣：先扣赠送再扣充值；**高级模型只扣充值** |
| 拦截开关 | `enforce`（默认 **false = 观察模式**：只记账不拦）；开启后低于阈值 → **402** + 充值引导 |
| 管理端充值/调账 | `POST /api/admin/users/:id/balance`（正数充值、负数扣减，写流水 + 审计 `balance.adjust`）；管理页用户弹窗可操作 |
| 客户端契约 | `/api/auth/me` → `user.balance`（总额/赠送/充值/到期/文案） |

**铁律**（`server/lib/balance.js`，`check-wiring.py` §19 有断言守）：

1. **钱不过期，赠品才过期** —— `paidMicro` 没有任何到期机制。
2. **消耗永远如实记账，允许透支** —— pre-check 与扣减之间有并发窗口，透支入流水，
   由下一次 pre-check 拦截。★ 曾因 `ensure()` 用非负夹取把负余额"消毒"成 0（欠费凭空消失），
   测试揪出后已改为 `signedMicro`。
3. **高级模型不吃赠送额度** —— precheck 要求充值余额过阈值**且 > 0**；
   ★ 曾漏判 `enforce` 把观察模式变成拦截，测试揪出。

**尚未做（需要你拍板或前置条件未满足）**：

- 客户端插件 UI（余额展示 / 充值入口）—— 属插件 0.26.0 批次，需实机验证。
- **订阅去无限化** —— Pro 的"3000 次/日"改成"每月发放额度 + 折扣"，需要先跑出人均成本才能定额度。
- **停售永久档** —— 政策动作：后台把「永久」价格条目停用即可（存量继续兑现，勿作废）。
- **充值订单自动化** —— 目前充值 = 线下收款 + 管理员调账（与"履约全人工"现状一致）；
  用户自助下单充值需要支付网关，属后续批次。
- **存量 3 个老账号的注册赠送** —— 不会自动补发（他们在 1.6.0 之前注册）；
  如需补发用管理页「调整余额」手动加。

### 8.2 观察模式 → 开启计费 的切换流程

```
① 现在（默认）：enforce=false
   网关照常扣减并记账（含透支），余额用尽也放行 —— 纯观察，不影响任何用户
② 配准单价（后台「成本与用量」→ 未配价模型清零）
③ 跑两周，看「人均成本」与「Top 消耗账号」
④ 后台勾选「余额不足时拦截」+ 设阈值（建议 ¥0.5~1，给用户缓冲）
⑤ 按需给存量用户调账（观察期的负余额此时会被拦，先充值或清零）
```

> ★ 切换前必读：观察期里老账号余额可能是负的（他们从 0 开始扣）。开启拦截后这些账号会被
> 402 拦住——要么先给他们充值，要么把负余额清零（管理端负数调账会被拒，用正数调平）。

### 8.3 三档结构对照（原设计 → 现状）

| 来源 | 设计 | 现状 |
|---|---|---|
| 注册赠送 | ¥6 / 30 天 / 限基础模型 | ✅ 已实现（配置可改） |
| 充值余额 | 永不过期 / 主路径 / 按标价全模型 | ✅ 已实现（管理端人工充值；自助充值待支付自动化） |
| 订阅额度 | 每月发放 / 不结转 / 解锁全模型 + 折扣 | ⏸ 未实施（等人均成本数据定额度；现阶段 Pro 仍是"3000 次/日"） |

### 8.4 其他必须处理项（沿用原清单）

- **存量永久会员必须兑现**：线上已有永久订单，属契约。做法：停售新永久档（后台停用价格条目），
  存量继续有效；或提供等值转余额让用户自愿选择。
- **退款与凭证**：充值余额是"没花完的钱"，流水已在 `user.balance.ledger`（每账号留最近 50 条），
  退款政策待定。
- **合规**：面向公众提供生成式 AI 服务在国内需履行算法备案等义务，建议在做大之前确认。
- **「自带 Key 永不限制」**：precheck 的 402 文案里明确给出「接入自己的模型通道」这条路（安全阀）。

## 9. 已知限制

- **只统计成功转发**（上游 < 400）。上游 4xx/超时是否已产生成本，阶段一不追踪。
- **`byModel` 是全时段累计**，不按窗口截断（字段名 `byModelAllTime` 已明示口径）。
- **单价表不存历史**。改价后，历史记录的 `costMicro` 是**当时价格**算出的（已落库、不重算），
  但后台看板的「按模型累计」也是历史值累加——**改价只影响之后的新调用**。
- **未配价模型按 0 计**，所以看板数值是**下界**，不是真实成本。
