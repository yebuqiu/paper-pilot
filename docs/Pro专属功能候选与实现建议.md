# Pro 专属功能：候选清单与实现建议

> 起因：用户提出「期刊分区列这类功能，Pro / 体验期用我的默认密钥，之后用户自己填自己的密钥」，
> 并问还有哪些功能适合这么做。
> 结论先行：**这个思路是对的，而且判据只有一条**；但**当前真正符合条件的只有一个功能**。

---

## 0. 判据（一条就够）

> **只有「消耗你（运营者）的密钥 / 配额 / 服务器」的功能，才适合做 Pro 专属。**
> 纯本地计算的功能锁掉是**净亏**——省不下一分钱成本，只伤口碑。

这条判据和 AI 网关完全同源：付费墙的本质是**替用户垫付了真金白银**，而不是"把功能关小一点"。

---

## 1. 现状盘点：仓库里哪些功能真的花了「你的」资源

| 功能 | 消耗谁的资源 | 现状 | 是否适合分层 |
|---|---|---|---|
| 官方 AI 网关（模型调用） | 你的上游 token 成本 | **已分层**（模型档 × 次数 × 余额） | ✅ 已做，无需再动 |
| **期刊分区列（easyScholar）** | **你的 `ES_OFFICIAL_KEY` 配额** | 全体免费用内置 Key | ★★ **最该做** |
| 被引量列（Semantic Scholar） | 公共接口（可配你的 S2 Key 提速） | 走公共限速 | ⭕ 可选（成本≈0，卖"稳定"） |
| 翻译（免密钥引擎） | 公共 / 无主 | 全体可用 | ⭕ 可选（同上） |
| 补全文（Unpaywall / Sci-Hub） | 公共 | 全体可用 | ⭕ 可选 |
| 知网/万方元数据（`cn-fetch.js`） | 逆向签名 `_PS_SECRET` | 全体可用 | ❌ 不适合 |
| 其余全部（标签治理 / 附件体检 / 笔记卡片 / PDF 对照翻译 / MCP / 数据列 / arXiv 检索 / 参考文献入库…） | **无**（纯本地或公共免费） | 免费 | ❌ 不该锁 |

**结论：现在真正符合条件的只有「期刊分区列」一个。**
其余候选都得**主动引入**一份运营者资源（买一个 Key / 接一个付费服务）才会形成合法的 Pro 权益。
「知网元数据」看起来像候选，但它是**逆向签名**——随时可能被对方轮换整段失效，拿它当付费权益等于卖一个会烂掉的东西。

---

## 2. 建议做的（按性价比排序）

1. ★★ **期刊分区列（easyScholar）** —— 你**现在就在替全体用户垫付**这笔配额，是唯一"已经在花钱"的功能
2. ⭕ **被引量 / 引文数据**：买一个 Semantic Scholar 官方 Key 给 Pro，免费用户继续走公共限速
   —— 成本≈0，但体感差异明显（更少 429 / 更稳）
3. ⭕ **稳定的翻译通道**：配百度 / DeepL Key 给 Pro，免费继续用免密钥引擎
   —— 卖的是「**不会突然被限流**」，这是可感知的价值
4. ⭕ **更强的补全文渠道**（若将来引入付费渠道）

> 2/3/4 的共同点：**边际成本极低但"稳定性"差异明显**。这类权益便宜、好讲、不伤口碑，
> 适合用来把 Pro 的权益从"只有 AI"扩充成"一整套"。

---

## 3. 更安全的中间形态：锁「上限」而不是锁「开关」

对纯本地功能，如果确实想给 Pro 价值，用**配额 / 上限**而不是"能不能用"：

| 形态 | 例子 | 为什么安全 |
|---|---|---|
| 单次条数上限 | 批量分析 / 附件体检：免费一次 N 条，Pro 不限 | 只有重度用户会碰到 |
| 并发数 | 同时跑几个后台任务 | 免费用户基本无感 |
| 导出上限 | 导出条数 / PDF 对比页数 | 边界场景 |
| 快照数量 | 配置快照保留份数 | 同上 |

这套与 `docs/账号与会员体系-优化建议.md` §20 末尾已列的「非 AI 功能分层」**完全一致**
（当时列为"未做，供决策"）——它比"锁开关"高明的地方在于：**免费用户的日常路径一点没变**。

---

## 4. 不建议做 Pro 专属（明确劝退）

**纯本地功能一个都别锁**（见 §1 末行）。三个理由：

1. **零边际成本** —— 锁了不省钱，纯属自伤。
2. **把已免费的功能改成收费 = 降级存量用户** —— 这是唯一**不可逆**的伤害。项目才刚起步，
   为了一点 Pro 价值去得罪已经装好的免费用户，账算不过来。
3. **与对外承诺冲突** —— 插件本体 Apache-2.0、承诺"功能永久免费 / 算力按量付费"。
   一旦出现"这个功能要钱"，整个叙事就崩了，而叙事本身就是获客手段。

---

## 5. 若做分区列：两种实现 + 一个必须先知道的前提

### ⚠️ 前提：内置 Key 是**明文公开**的，做不成真正的安全边界

`rank-column.js` 里 `ES_OFFICIAL_KEY` 就是明文常量（源码注释也写明"此值随插件公开分发"），
而且它已在**已泄漏待轮换清单**里（记忆分册 01）。
⇒ 任何人解包 xpi 都能直接拿走。**方案 A 只是"体验分层"，不是"防得住"。** 这点必须先认清。

### 方案 A：插件本地软门控（**已实现，0.41.0**）

```js
_officialKeyAllowed() {          // 内置官方 Key 的使用资格
  if (typeof Account === "undefined" || !Account) return true;        // 模块未加载 → 放行
  if (!Account.isLoggedIn()) return false;                            // 未登录 → 须自带 Key
  if (Account.isPro()) return true;                                   // 专业版 → 可用
  const a = Account.ai();
  if (a && a.reason === "trial") return true;                         // 新用户试用期 → 可用
  if (!a || a.reason === "unknown") return true;                      // 旧服务端 → 放行
  return false;                                                       // 免费版（试用结束）
},
esKey() {
  const custom = Prefs.get("easyScholarKey", "").trim();
  if (custom) return custom;                    // ① 自带 Key 永远优先、不限套餐
  return this._officialKeyAllowed() ? String(this.ES_OFFICIAL_KEY || "").trim() : "";
},
```

- `_esEnabled()` 天然跟随（Key 为空即不启用在线源），**但必须补清晰的引导文案**：
  设置页的分区列提示 + 列内空态提示要写清「免费版请填写自己的 easyScholar Key，或升级专业版」，
  否则免费用户只会看到"分区列不显示"，误判成 bug。
- **旧服务端 / 探测不到套餐 → 一律放行**（沿用既有纪律：*客户端不知道时绝不自作主张锁用户*）。

### 方案 B：服务端代理（正规，推荐中长期）

把 easyScholar 调用挪到账号后台（如 `GET /api/jcr?name=`），服务端持 Key、按套餐或余额计量。

| | 方案 A 软门控 | 方案 B 服务端代理 |
|---|---|---|
| 改动力度 | 1 个函数 + 文案（发一次 xpi） | 服务端新接口 + 计量 + 发版 |
| 密钥位置 | **仍在 xpi 明文里** | 只在你服务器上 |
| 是否防得住 | ❌ 解包即可绕过 | ✅ 真边界 |
| 能否计量/限速 | ❌ | ✅ 可 |
| 顺带收益 | — | **可把已泄漏的 Key 换掉** |
| 与既有体系 | 独立 | 复用 AI 网关的余额/计量/限速 |

## 7. 我的建议（排序 + 进度）

1. ✅ **已做：方案 A + 分区列**（插件 0.41.0，2026-10-15，落地记录见下）
2. ⏳ **待做：补 2~3 项「成本≈0 的稳定性权益」**（S2 Key / 翻译 Key）
   —— **前置：需要你先申请/购买这些 Key**，否则只能搭机制、无法真正生效。
3. ⏳ **待做：迁到方案 B**（服务端代理）—— 前置：把你的 easyScholar Key 配到 `server/data/` +
   决定是否轮换那个已泄漏的 Key。
4. ✅ **纯本地功能一个都别锁**（本次未动）；真要做就用 §3 的「上限」形态。
5. 每次改动前的唯一必问：**存量免费用户会不会被降级？** —— 这是唯一不可逆的代价。

### 第 1 项的落地记录（插件 0.41.0，2026-10-15）

| 项 | 内容 |
|---|---|
| 判定 | `rank-column.js _officialKeyAllowed()`：自带 Key 优先 → 已登录且（专业版 或 试用期）→ 否则不给 |
| 三态状态 | `esStatus()` = `ok` / `off`（用户自己关）/ `need_key`（需自带 Key），供设置页给可执行指引 |
| 文案 | `prefs.xhtml` 的 placeholder 与 hint 改写；`prefs-pane.js` 状态行在 `need_key` 时转警示色并写明原因 |
| 不白屏 | 免费版仍走「自定义 JSON → 内置数据集」兜底（`lookup()` 的 else 分支），**列不会空** |
| 老用户保护 | 未登录 / 旧服务端（unknown）/ 判定抛错 **一律放行**；只有「已登录且明确非 Pro 非试用」才拒绝 |
| 测试 | 新增 `test/rank-gate.test.js`（23 项）+ `check-wiring.py` §34（8 条，含**内置 Key 引用计数 == 2**，防绕过） |

> ⚠️ **这是一次对存量免费用户的降级**（他们此前用内置 Key、之后需自带 Key）——由你明确拍板。
> 缓解手段：内置数据集继续兜底、自定义 JSON 不受影响、Pro/试用/自带 Key 全不受限；
> 设置页会直接写明原因，避免被当成 bug。

### 第 2 / 3 项的前置输入（需要你）

| 项 | 需要你提供 | 不给的话 |
|---|---|---|
| 2. 稳定性权益 | 一个 Semantic Scholar API Key、一个翻译引擎 Key（百度/DeepL） | 只能先把机制搭好，Key 留空则行为与现在完全一致 |
| 3. 方案 B 代理 | 你的 easyScholar SecretKey（配进 `server/data/`，不进 git）+ 是否轮换旧 Key | 服务端接口可以写好，但没有 Key 就无法启用（和支付网关同一套 fail-safe） |
